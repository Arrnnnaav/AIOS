# GhostCursor investor deck — reviewed content source

Status: product-evidence draft for two 10-slide showcase decks

Audience: pre-seed accelerators, design partners, and early enterprise buyers

Rule: a bracketed item is deliberately unresolved. It must remain visibly a
placeholder in every generated deck until the founder supplies a verified fact.

## Narrative in one sentence

GhostCursor turns approved procedures into local, verified, in-app guidance for
native Windows software—helping a person complete work while keeping every
action human-controlled.

## Slide 1 — The interface should understand the outcome

**Headline:** Software should understand what the human is trying to accomplish.

**Subhead:** GhostCursor is a local workflow guidance layer for native Windows
applications.

**Proof line:** State a goal. See one trusted next step. Act yourself. Verify the
result.

**Footer:** GhostCursor · pre-seed product narrative · September 2026

Visual intent: one dark PowerPoint-like window, one cyan focus ring, and a
minimal four-stage path: goal → guide → human action → verified outcome.

## Slide 2 — Software training breaks at the moment of work

**Headline:** The PDF knows the procedure. It cannot see where the employee is
stuck.

**Three failure moments:**

1. A new employee switches between a manual, a video, and the live application.
2. A senior teammate repeats screen-sharing support for the same workflow.
3. IT receives “the app is not working” without the failed step or live context.

**Takeaway:** Training, execution, and support are separate systems even though
the failure happens in one live interface.

Visual intent: a left-to-right broken journey with context loss between each
handoff, not a bullet-heavy problem slide.

## Slide 3 — Native desktop is the neglected surface

**Headline:** Browser overlays stop where critical Windows work begins.

**Contrast:**

| Traditional digital adoption | GhostCursor |
|---|---|
| Usually depends on application or webpage integration | Reads the live Windows accessibility surface |
| Replays authored walkthroughs | Selects only an active, signed workflow |
| Measures clicks and completion events | Verifies the declared post-action state |
| Guidance and automation can blur | The user remains the only actor |

**Examples to validate with customers:** SAP GUI, engineering tools, internal
GCC applications, core-banking terminals, hospital administration software.

Visual intent: browser-shaped boundary on the left; diverse native application
windows continuing beyond it on the right. Do not claim competitor feature
absence without a current cited market comparison.

## Slide 4 — A trusted loop, not a cursor trick

**Headline:** Observe → authorize → guide → verify → learn.

**Loop:**

1. The user states a goal.
2. An enabled signed plugin authorizes a bounded workflow.
3. GhostCursor highlights one reviewed control without clicking or typing.
4. The user performs the action.
5. The application’s next state proves success or fails closed.
6. Non-positional UI identity may be learned locally for the next run.

**Trust strip:** Local by default · no screenshots in normal operation · no
input synthesis · stop/pause always available.

Visual intent: one continuous loop around a live application frame. Use the
safety rail as a small product signature, not a full UI screenshot.

## Slide 5 — The architecture already proves the hard parts

**Headline:** The core is application-agnostic; workflows arrive as signed data.

**Current verified state:**

- Three signed active plugins: Synthetic, VS Code, and Excel.
- Six active workflows in the production catalog.
- Two Excel workflows each completed 3/3 human desktop acceptance with UIA-only
  grounding on the accepted executable version.
- A data-only VS Code workflow was added and accepted without production Python.
- Five PowerPoint workflows are measured and quarantined pending independent
  review and acceptance; they are not presented as active.
- Current hermetic gate: 1,208 passed, 71 deselected on commit `ef7a555`.

**Takeaway:** Adding app coverage no longer requires adding app-specific logic
to the core executor.

Visual intent: an iceberg diagram—small native core below a row of signed
plugin cards. Keep accepted and quarantined states visually distinct.

## Slide 7 — The workflow is the compounding asset

**Headline:** Capture once. Guide many. Resolve the exceptions. Improve the
procedure.

**Product expansion:**

1. **Capture** — an expert performs a task; a candidate procedure is reviewed.
2. **Guide** — employees receive in-context, stepwise help.
3. **Verify** — each expected application state is checked.
4. **Resolve** — known friction is diagnosed; unresolved failures become
   context-rich escalation.
5. **Insights** — aggregated workflow friction shows what the organization
   should fix.

**Privacy boundary:** manager analytics should describe workflow-level friction,
not rank individual employees.

Visual intent: a five-part flywheel with evidence flowing back into Capture.

## Slide 8 — Land with one workflow, expand by app and outcome

**Headline:** A paid pilot can prove value before a platform sale.

**Commercial sequence:**

1. Fixed-scope pilot: one team, one application, one approved workflow.
2. Team deployment: additional workflows and local manager/diagnostics.
3. Enterprise platform: plugin lifecycle, workflow governance, support routing,
   and aggregated insights.
4. Distribution: implementation partners and software vendors publish reviewed
   workflow packs.

**Pricing hypotheses—not claims:** paid pilot → annual platform + seats/apps →
premium Resolve/Insights. Validate willingness to pay before publishing prices.

**Placeholders:** `[PILOT PRICE]`, `[ANNUAL CONTRACT HYPOTHESIS]`,
`[FIRST DESIGN PARTNER]`.

Visual intent: a four-rung expansion ladder with explicit validation labels.

## Slide 9 — Defensibility grows from verified outcomes

**Headline:** The moat is not the overlay. It is trusted workflow intelligence.

**Five compounding assets:**

- reviewed workflow graph;
- resilient application understanding across versions;
- organization-specific procedure knowledge;
- outcome verification rather than click tracking;
- resolution memory for recurring failure patterns.

**Technical discipline:** signed local bundles, exact application identity,
fail-closed ambiguity, one canonical authorization gate, and no executable
guidance without active plugin authority.

Visual intent: five concentric layers around “verified outcome,” with the cursor
outside the moat to make the point that it is only an interface.

## Deck-wide visual system

- Format: 16:9 widescreen.
- Mood: calm, technical, high-trust; Apple-inspired restraint without copying
  Apple product chrome.
- Background: near-black navy `#080B12`; elevated surfaces `#111827` at 88–94%
  opacity.
- Primary text: `#F5F7FB`; secondary text: `#A8B2C3`.
- Accent: cyan `#26C6DA`; confirmation green `#48D597`; refusal amber
  `#FFB454`; error coral `#FF6B6B`.
- Typography: Aptos Display for headings, Aptos for body, one numeric mono
  accent only when evidence benefits from it.
- Spacing: 8-point base; 64px outer margins; large empty fields; no more than
  one visual claim per slide.
- Shape language: 16–22px radius, 1px cool-gray borders, restrained glass fills,
  no decorative drop-shadow stacks.
- Motion: Fade by default. Morph only for two explanatory sequences: the broken
  onboarding journey becoming the trusted loop, and the workflow flywheel
  expanding into the 90-day plan. No spins, bounces, or unrelated motion.
- Accessibility: minimum body equivalent 20pt, high contrast, never rely on
  color alone for accepted/quarantined/failure states.
